# iOS implementation roadmap

Status: repository version 0.4.0, updated October 4, 2026. The Capacitor iPhone host, explicit iOS routing, Swift bridge, and SQLite text library are implemented. The current milestone covers durable drafts, capture/edit/delete/undo, search, Gems, tags/checklists, profiles at the repository boundary, and local Recovery.

See [iOS development](ios-development.md) for build commands and [verification results](ios-verification.md) for recorded checks. Signed installation and physical-device behavior remain unverified; the [iPhone device checklist](ios-device-checklist.md) is the next handoff. The phases below retain the broader roadmap scope, including unfinished media, backup, sync, and distribution work.

## Recommended approach

Keep React, TypeScript, Vite, and Capacitor. Continue the iOS host and Swift implementation of the existing native bridge. Reuse the React composer initially, use native SQLite for durable storage, and reuse the Rust protocol for linked-device sync. This preserves the existing interface and offline architecture while concentrating new work on iOS integration.

Deliver three distinct milestones:

1. **Buildable shell:** opens in the iPhone simulator and on a development device; native bridge registration works. This is an engineering milestone, not a usable library.
2. **Usable offline app:** capture, durable drafts, search, tags, Gems, checklists, media, locations, Recovery, and portable backup work on an iPhone.
3. **Connected beta:** the offline app interoperates with Android and Windows over LAN and can be distributed through TestFlight. Widgets and shared hashtags are subsequent scope unless essential for the initial release.

Assume an iPhone-first release and foreground sync. Decide explicitly whether iPad is supported in the first distribution. A full SwiftUI rewrite would substantially expand this port's scope.

Capacitor core, CLI, Android, and iOS resolve to **8.5.2**. The repository requires Node **22 or newer**, Xcode **26 or newer** for iOS, and an iOS deployment target of **16.4**. Swift Package Manager supplies native dependencies. This branch has no Rust iOS feature/build scripts or iOS Keychain identity; the separate feasibility snapshot is outside this milestone.

## Phase 1 — Build the host and prove the native boundaries

The host, platform routing, registered plugin, simulator commands, and unsigned simulator build are implemented. The remaining boundary check is signed device installation. The Rust prototype is separate future work for this branch. Original scope follows:

- Establish the frontend test/build baseline before changes. Add `@capacitor/ios` matching the lockfile and generate the iOS host. Choose a bundle identifier available to the signing team; keep it stable after distributing builds.
- Use the dependency-manager configuration generated by the pinned Capacitor CLI and document it. Commit the native project and relevant lockfiles, excluding generated builds and signing secrets.
- Add `ios:sync` (`npm run build && cap sync ios`) and `ios:open` (`cap open ios`) scripts. Keep the deployment target at iOS 16.4 to match the Tailwind 4 / Safari baseline.
- Add `ios` to `Platform`; use `Capacitor.getPlatform()` to distinguish Android and iOS. Route iOS to its native plugin. Set `nativeCapture` and `widgets` false initially and add explicit capabilities for sync, sharing, Recovery, and media as needed.
- Audit startup calls and Settings/Devices screens so unavailable functionality is hidden or clearly unavailable. Never silently route an iPhone installation to sample data, or return fabricated successful writes.
- Register a minimal Swift `Museamo` plugin and prove one native round trip plus `dataChanged`. Separate the app-facing interface types from the preview implementation if it simplifies contract testing. [Capacitor custom iOS code](https://capacitorjs.com/docs/ios/custom-code).
- In a small prototype, compile the Rust core for `aarch64-apple-ios` and `aarch64-apple-ios-sim`, link it to Swift, and exercise a JSON call/callback. Add Intel simulator support only if a developer or CI runner needs it. This validates bindings and dependencies before sync becomes the critical path.

The host is already implemented; use `npm ci`, `npm run ios:build`, and `npm run ios:open` from a checkout rather than regenerating it.

**Exit checks:** simulator build succeeds; signed development build launches on an iPhone; platform routing is correct; plugin calls/events work; missing capabilities do not cause startup errors. Record the Rust prototype result and any blockers.

## Phase 2 — Durable text capture and the core library

The text repository and bridge are implemented with local revisions and Recovery. Hardware lifecycle validation remains; sync journaling/enrollment is deferred. Original scope follows:

- Implement a Swift repository backed by SQLite in the app's private Application Support storage. Keep a serialized write boundary and explicit, tested migrations; do not use destructive migration fallback.
- Match existing logical data contracts: stable UUIDs, timestamps, tags and normalization, checklist completion, profiles, durable drafts, cursor pagination, edit revisions, and local Recovery. Use the existing native stores as behavioral references; iOS does not need to copy Room's physical schema.
- Implement the bridge methods required for library loading, queries, create/edit/delete/undo, stars, tags/checklists, profiles, drafts, and Recovery. Use the React composer by disabling Android's native-capture path on iOS.
- Commit a draft's entry and remove that draft in one transaction, preserving its entry UUID to prevent duplicate posts. Persist edits before suspension; validate interrupted saves and rapid repeat taps.
- Preserve the existing stale-edit behavior, timestamp rules, and hashtag semantics. Emit `dataChanged` after durable changes and reconcile data on app activation.
- Design the revision/journal boundary with sync in mind now: use the existing envelope contracts and transaction requirements. If journaling is deferred, specify and test a one-time enrollment migration before Phase 5; do not retrofit it informally after real libraries exist.

**Exit checks:** create and edit thoughts in airplane mode; terminate and relaunch the app; verify entries and unfinished drafts survive. Exercise pagination while new entries arrive, duplicate commit attempts, checklist ordering, undo, Recovery, and failed storage operations. Reuse fixtures in `test-fixtures/` for formatting and hashtags.

## Phase 3 — Media, locations, and portable backups

- Implement system photo/video selection, copies of immutable originals into private storage, metadata/checksums, thumbnails, attachment ordering, and cancellation cleanup. Keep binary data out of JSON bridge messages.
- Prototype restricted WKWebView media delivery early. Resolve only registered attachment IDs and validate video byte-range/seeking behavior. Android's `/_media/` route and its HTTPS origin cannot simply be assumed to work on iOS. Test external links, map tiles, and embedded players under the actual iOS origin too.
- Preserve originals even when another platform cannot decode their codec. Exercise HEIC, orientation metadata, large videos, low disk space, interrupted imports, and cleanup of files retained by drafts or Recovery.
- Implement foreground Core Location access, permission-denial feedback, the automatic-location preference, timeout/cancellation, and safe geocoding updates. Replace Android-specific permission wording. Add only the usage descriptions required by the chosen APIs.
- Support the current **v5 ZIP backup**, including Recovery and referenced originals, and older formats accepted by the existing native apps. `docs/architecture.md` contains older format milestones; use current code and `docs/offline-sync.md` for the current contract.
- Use native document pickers for import/export. Preserve bounds, checksum validation, path validation, collision/remapping semantics, staging, and rollback. Keep device keys, pairing state, and drafts out of portable archives.

**Exit checks:** round-trip real Android and Windows archives through iOS and back; compare IDs where preserved, text, tags, completion, locations, Recovery, and original-file hashes. Invalid/interrupted imports leave the previous library intact. Media and drafts survive relaunch.

**Milestone:** the app is now useful as a standalone offline iPhone library, with backups for transfer before LAN sync is ready.

## Phase 4 — iPhone usability and lifecycle hardening

- Validate safe areas, the home indicator, small displays, landscape behavior, dark mode, and keyboard avoidance. Audit existing `visualViewport` handling and sheet focus behavior on an actual iPhone.
- Test Tiptap selection, paste, formatting, hashtag completion, scrolling, and draft retention through app switching and interrupted picker flows.
- Check VoiceOver labels/order, text enlargement, reduced motion, touch targets, and loading/error feedback. Include iPad layouts and multitasking if shipping iPad support.
- Exercise background/foreground transitions without relying only on browser visibility events. Native lifecycle callbacks must preserve drafts and refresh the current view.

**Exit checks:** run a written device checklist with the oldest supported OS/device combination available and a current iPhone; no blocked composer controls, lost edits, or inaccessible primary actions.

## Phase 5 — Interoperable LAN sync

- Package Rust for device and simulator into an XCFramework, using a small C ABI as the initial binding approach. Define ownership, error handling, callback threading, shutdown, and panic containment explicitly; add a reproducible `scripts/build-sync-ios.mjs` command.
- Implement the native `Platform` callbacks for identity, signing, persistence, envelopes, receipts, Recovery, and media transfer. Store identity secrets using Keychain with an explicit access/backup policy; keep private keys and low-level signing operations outside the WebView API.
- Preserve transactions that couple saved mutations, revision allocation, history, and projection. Acknowledge received changes only after durable application. Reuse the Rust protocol and cryptography rather than porting them to Swift.
- Adapt discovery separately from transport. The current coordinator owns `mdns_sd::ServiceDaemon` and advertises `_museamo._tcp.local.`. Prefer Apple Bonjour APIs for iOS, providing discovery hints to the Rust coordinator and exposing truthful discovery status. Refactor this boundary if necessary.
- Declare the local-network usage description and Bonjour service type. Test permission denial/recovery on hardware. If retaining raw multicast discovery, investigate Apple's multicast entitlement rather than assuming existing socket code can ship unchanged. Preserve manual-address pairing. [Apple local-network guidance](https://developer.apple.com/documentation/technotes/tn3179-understanding-local-network-privacy).
- Start/resume sync while the app is active, retain a visible Sync now action, and checkpoint/stop safely on suspension. Use only limited background completion when appropriate. Do not promise a continuously running LAN listener: iOS restricts background execution. [Apple background execution guidance](https://developer.apple.com/forums/thread/685525).
- Implement full matching-code verification and the separate combine-library consent. Keep shared-hashtag collaboration behind its own capability until its separate flow is implemented and tested.

**Exit checks:** pair iOS↔Android and iOS↔Windows; verify a three-device library, simultaneous edits, deletion conflicts, Recovery, device removal, attachment retries, offline edits, denied LAN permission, changed Wi-Fi, and interruption during transfer. Confirm resume catches up and identical deliveries do not create duplicates. Existing Android and Windows protocol tests still pass.

## Phase 6 — Reproducible builds and TestFlight

- Verify the configured macOS CI job for Swift tests and an unsigned simulator build on a hosted runner. UI tests currently run locally. Expand CI with Rust Apple builds when that integration lands.
- Add a separate iOS release command/workflow; current release orchestration assumes local Windows builds. Keep the existing Android/Windows outputs working.
- Configure signing team, app identifier, version/build numbers, icons, launch presentation, archive/export settings, and App Store Connect/TestFlight access. Development-device installation and TestFlight distribution are separate deliverables.
- Review the privacy manifest and required-reason API declarations for the app and included SDKs; provide accurate privacy/support information and permission explanations. Retain repository license notices and resolve distribution licensing questions before public release.
- Verify Apple's SDK requirement again before upload. At this review, App Store Connect requires iOS 26 SDK or later for uploads starting April 28, 2026; that build SDK requirement does not force an iOS 26 minimum deployment target. [Apple SDK requirements](https://developer.apple.com/news/?id=ueeok6yw).

**Exit checks:** a fresh checkout builds using documented commands; an archived build installs via TestFlight; upgrading preserves an existing library; backups restore successfully; release credentials remain outside the repo.

## Follow-on features

- **WidgetKit quick capture:** begin with a widget that opens the correct capture profile via a deep link. Add shared App Group metadata only as needed. WidgetKit uses a separate extension and navigation model; Android widget activities cannot be reused. [Apple widget documentation](https://developer.apple.com/documentation/WidgetKit/Creating-a-Widget-Extension).
- **Native Swift composer:** consider after measuring the React editor on hardware, if editing quality or launch speed requires it.
- **Shared hashtags:** port invitations, participant roles, revocation, and sharing storage separately from personal-device sync; use `src/sharing.ts` and existing native implementations as the contract.
- **Share extension/App Intents:** optional new capture entry points with explicit draft ownership and extension-safe storage access.
